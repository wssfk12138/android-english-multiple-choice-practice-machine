# 英语刷题机整体整改方案（历史逐条核对版）

核对日期：2026-09-16。对象：Android 开发权威树；Windows、Android 公测副本与 DeepSeek Harness 本体保持独立。本文是重新整理的决策方案，不等同于启动实施授权。

## 1. 本次核对的原始要求

当前任务的直接要求是：读取任务 `codex://threads/01a0a2dc-1ac8-7c80-9740-4b73f231a02c`，再读取该任务提到的 DeepSeek Harness 中英语刷题机相关对话，逐字逐句核对用户要求，参考两版旧方案，重新做整体方案。

指定任务中保留的用户原话包括：

- “读取DeepSeekharness中英语刷题机项目下的所有对话历史，根据我昨天的要求重新做一个整改方案，所有需要重新设计的UI界面由你来重新设计，并最终递交给我一份完整的待我决定的事项清单”。
- “我无法打开你上次任务之后留给我的几项文件”。

指定任务的旧交付还明确写过：只完成设计和方案，不修改 Android 源码；要覆盖单词本、每日复习、单词显示、设置、Model/API、导入、更新、同步、诊断、错题本/练习和 AI 助手；使用合成数据；把确定问题、待实测风险和决策项分开。

DeepSeek Harness 工作区登记的英语刷题机项目包含 3 个顶层会话；指定任务的历史摘要记录为 11 个子会话、14 份日志。历史中还能直接核对到以下长期要求：

1. Android 与 Windows、公测与内测独立；不得整仓覆盖、隐式同步、自动推送或发布。
2. 题库导入必须保留来源证据、草稿校对和批准入库门禁；扫描 PDF 无可靠文字层时提示人工处理，不能伪装 OCR 成功。
3. API Key 只能进原生 SecureStore/受保护侧文件，不能进 SQLite、日志、源码或公开上下文。
4. 错题记录、单词复习、翻译队列和跨设备同步要保护既有数据；修复使用稳定键、旧值指纹、事务和可回退快照。
5. 用户明确要求过：单词翻译在退出答题界面后启动；单词本支持分阶段复习和 5/10/20 词额外巩固；错题保留当前快照、正式重做轮次和七天回收站。
6. 最近一轮 UI 原话已收敛为：平板横屏减少无效卡片和重复导航；真题原句不折叠；“今日到期”改称“每日一背”；巩固与搜索筛选合并；删除“本句语境”；词形标签使用中文；生成和显示分离；设置入口进入各自独立内容；翻译缺字段由后台补全，默认输出由后台处理且前端不暴露上限控件。

旧的 2026-09-15 方案是审阅稿，提出了 B 方案、默认展开、accordion、模型目录折叠、回填策略等 8 项待决定事项。随后 2026-09-14 的 R3 方案记录了更晚且更具体的确认：N1–N4 均选 A，N5 为“输出由后台默认不设上限”，附加建议只采纳 O1、O6；并记录 R1–R11 已按确认规格实施，部分仍待真机验收。

- 用户后续明确选择覆盖旧方案中的建议；

## 3. 总体目标与边界

目标是建立一条可审计的整改链：题库内容正确、词汇生成不丢数据、横竖屏信息层级清楚、设置入口真实可达、首次加载不被后台任务阻塞，并能在 Android/Windows 各自验证后再受控交付。

本轮整体方案覆盖五条线：

| 线 | 目标 | 结果定义 |
|---|---|---|
| A 题库与 ESQ | 修复 Part B、完型空位、题干/选项边界和固定段映射 | 每项有来源证据、稳定键、dry-run、可回退升级 |
| B 词汇与翻译 | 生成/显示分离、词形中文化、真题原句与模型例句分开、缺字段后台补全 | 不覆盖人工字段；队列可暂停续传；合法空值不重复请求 |
| C UI 与信息架构 | 落实平板横屏 R3，并保持手机竖屏与 Windows 适配 | 页面入口、折叠、操作、响应式行为可追溯 |
| D 性能与启动 | 观察并量化首页/单词本首次载入线索 | 记录事实与推测；不把一次采样写成已修复 |
| E 交付与保护 | 分平台构建、安装、验收、提交和发布 | 每一步单独授权，产物身份与数据保护可核对 |

## 4. 已确认、已实施和暂停项

### 已确认，实施时不再重复询问

- 单词本横屏采用统一工具栏、左约 30% 词表、右约 70% 详情；不增加布局切换器。
- “每日一背”统一文案；巩固区与搜索/筛选合并；保留 5/10/20 入口。
- 真题原句在答案显示后直接展示并左对齐；删除“本句语境”独立栏目。
- 删除按钮在错题条目右侧直出，但仍保留确认。
- 设置首页只呈现分组和入口；同步、更新/远程题库、诊断为独立内容；模型目录默认收起但筛选常驻。
- API 配置保留紧凑摘要，同一时间展开一项；移除前端输出 Token 上限控件及兼容卡；请求层按协议能力决定是否省略上限，不能发送虚构无限值。
- 翻译生成与显示开关彻底分离；词形标签中文化；旧 `contextualMeaning` 保留兼容但不再作为新生成目标。
- 历史缺字段采用后台批量补全：统计数量、等待可用配置、小批量、暂停/续传/失败重试、保护人工字段。
- 附加建议只纳入 O1、O6；O2–O5 不扩大本轮范围。

### 已实施但需要区分验证层级

- R1–R11 的源码整改、N1–N5 对应 UI/协议适配、451 条缺字段补全队列基础能力已有源码与合成验证记录。
- 设置分组、模型选择弹层、确认弹层、单词本/复习/错题/更新/导入等历史 UI 改动已有构建和定向测试。
- 最新内测安装基线为 alpha.89；该事实不能代替本次 R3 的新真机体验。

### 明确暂停或排除

- 平板横屏卡顿的独立性能修复仍暂停；本方案只要求在触碰相关路径时记录线索。
- 不把旧方案的多列网格、UI 方案切换器、O2 草稿徽标、O3 帮助清理、O4 状态徽标、O5 题库来源合并带入本轮。
- 不进行真实模型补全、真实 Key 调用、跨仓同步、公测发布、GitHub 推送或永久删除。

## 5. 分阶段实施顺序

### 阶段 0：基线冻结与授权核对

记录四类源码树、当前 Git 状态、安装包 versionCode/签名/哈希、数据库备份和 R3 入口。所有修复先建立清单，不整仓暂存。

### 阶段 1：题库内容闭环

按 F001–F036 和现有 R1–R3 清单处理。先 dry-run 展示命中、跳过、冲突；有可靠原卷/Word 证据才写回；固定段使用 `fixed_slots`，候选字母、显示字母和稳定键分开；未知或冲突项保留待人工校勘。验证解析器、内容块、纯文本路径、答案映射和旧会话兼容。

### 阶段 2：词汇数据与 API 协议

统一生成响应 schema：常用释义、音标、词性、词形、同反义/形近辨析、记忆提示、真题原句、模型例句、笔记分别建字段和显示策略。补全队列使用内容版本/时间戳条件写入；不覆盖人工编辑；缺少模型时等待而不是循环付费重试。对“后台不设上限”做请求级测试，验证各兼容协议的省略/能力协商和明确失败提示。

### 阶段 3：UI 与路由

先完成单词本、每日一背、设置、Model/API、同步、诊断和更新页，再核对导入、错题、AI 助手。每个设置入口必须对应真实页面；横屏两列、窄屏单列；触控目标约 44–48dp；长单词和长句可换行。

### 阶段 4：性能观察

仅在阶段 1–3 实际触碰的初始化、SQL、补全调度和渲染路径记录线索。分别计时首页、单词本首次进入/再次挂载、评分、额外巩固；记录设备、横竖屏、词条数、请求次数和队列状态。没有前后可比数据就只报告观察结果。

### 阶段 5：验证与受控交付

先跑受影响 Vitest/TypeScript/构建和 `git diff --check`，再按授权处理 Android Capacitor/Gradle、同签名覆盖安装和设备体验。Android 内测、公测、Windows 内测、公测分别核验；提交、推送、Release、通道更新和跨仓同步另行判断。
