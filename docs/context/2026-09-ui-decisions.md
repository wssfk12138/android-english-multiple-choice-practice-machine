## 一、单词学习页（横屏单词本首页「额外巩固」以下）

用户已确认：只动「额外巩固」以下（左列表 + 右详情），以上保持不变；不新增内容；只允许微调行距与收缩空间。

### 决定 1-1：列表每一行显示哪些信息

**现状与证据**
列表行实测 **234 设备像素 = 110 CSS px = 110 dp**。Material 的列表项只有三档：单行 56、双行 72、三行 88 dp。110dp **比"三行项 88dp"还高 25%**，而这一行当前装的是：

```
★ 高频词星标 | corruption | 遇到 2 次
腐败；贿赂；讹误
n. | 学习中 | ▾
```

即"词条 + 释义 + 词性/状态"，约 **两行语义**。也就是说：**内容只有两行，却按三行以上留白。**

列表卡可视高 **351 CSS px**，据此：

| 选项 | 行内保留 | 行高 | 可见行数 |
| --- | --- | ---: | ---: |
| 现状 | 星标+词条+遇到次数+释义+词性+状态 | 110 dp | **3.2** |
| **甲** | 词条 + 学习状态 | 56 dp | **6.3** |
| **乙** | 词条 + 音标 + 学习状态 | 56 dp | **6.3** |
| **丙** | 词条 + 释义 + 学习状态（去掉"遇到次数"和"词性"） | 72 dp | **4.9** |

**为什么需要你决定**
这直接决定列表"看得见多少词"，也决定"释义"要不要在左右两栏各出现一次（现在左列表右详情都显示释义，同一句话一屏里读两遍）。

**各选项的代价**
- **甲**：最省空间、6.3 行。代价是列表里看不到释义，只能靠点开右栏看；扫列表时不知道每个词什么意思。
- **乙**：同样 6.3 行，但多一个音标。代价同甲（没有释义）。
- **丙**：保留释义，扫列表时能直接读懂。代价是只能看 4.9 行，且释义与右栏重复。

**我的推荐：乙。** 理由有三条可核实的依据：
1. **Anki 的官方功能 `Browser Appearance`** 明确允许"定义一个只在列表里使用的模板，**只包含重要字段**"——即"列表用精简字段、详情用完整字段"是成熟产品的标准做法，不是我们为了压高度而妥协。
2. **Material 3 的 list-detail 规范要求**"每个列表项应该带元信息（日期、分类、标签）方便检索"——学习状态就是元信息，所以**不建议压到只剩一个单词**（甲偏空）。
3. 音标与右栏"词条 + 音标"呼应，用户扫列表时能顺带确认读音，成本为零。

**能否回退**：能。改的是行内模板与行高，不涉及数据；改错只需还原模板。

### 决定 1-2：左列宽度是否改为固定值

**现状与证据**
`styles.css:275`：

```css
.vocabulary-layout { grid-template-columns: minmax(300px,.85fr) minmax(390px,1.2fr); gap:15px }
```

实测左列 **374 CSS px**、右列 **527 CSS px**。而 **Material 3 的 list-detail 规范明确写**：

> "in a list-detail layout, the list should have a **fixed width**, while the detail pane should be **flexible**"

**为什么需要你决定**
现在两列都是弹性的，两个都会随窗口变化。左列只放"词条 + 一行释义"却占 374 px，而右列要放中文释义和英文长句，527 px 反而**比 WCAG 的可读性上限还窄**（WCAG 2.2 SC 1.4.8：中文每行不超过 40 字，16px 中文约需 640 px）。

**各选项的代价**
- **甲（保持弹性）**：不动代码，风险最低。代价是继续与规范不一致，且右栏偏窄的问题不解决。
- **乙（左列固定、右列弹性）**：符合规范，右列能吃到更多宽度，中文长句少换行。代价是改动布局声明，需在两个方向都验证一遍。
- **丙（左列固定 + 右列也设上限）**：右栏不至于过宽。代价是多一个需要维护的数值。

**我的推荐：乙。** 规范有直接条文，且正好解决"右栏偏窄"这个实测问题。左列固定值建议取 **340 CSS px**（比现在略窄，让右栏增宽约 34 px）。

**能否回退**：能，改一行 grid 声明。

### 决定 1-3：左列卡顶与右列卡顶是否取齐

**现状与证据**
列表卡顶 y=411 设备像素，详情卡顶 y=402，**差 19 设备像素（约 9 CSS px）**。截图里能看出右栏比左栏高一点点。

**为什么需要你决定**
这条属于你提的"纵向可以对齐的卡片也可以对齐"。修它几乎无成本，但会让顶部那条线更整齐。

**代价**：甲（不动）视觉上有轻微错位；乙（取齐）需要统一两栏容器的外边距，改动很小。

**我的推荐：乙（取齐）。**

**能否回退**：能。

### 决定 1-4：行高取 56dp 还是 72dp

**现状与证据**：见决定 1-1 的表格。56dp → 6.3 行；72dp → 4.9 行。

**为什么需要你决定**
这取决于你更看重"一屏看更多词"还是"每行读起来更松快"。

**各选项的代价**
- **56 dp**：一屏 6.3 行。代价是行与行之间较紧，触控目标 56dp 仍高于 Material 的 48dp 下限，无障碍没问题。
- **72 dp**：一屏 4.9 行。代价是少看约 1.4 行，换来更舒展的行距。

**我的推荐：56 dp。** 因为本轮的核心痛点就是"只看得见 3 行"，56dp 仍满足 Material 与 Android 的 48dp 触控下限，不牺牲无障碍。

**能否回退**：能，改一个数值。

### 决定 1-5：选中行要不要加强视觉指示

**现状与证据**
当前选中行只有浅色底（截图里 `corruption` 那一行）。而 **Material 3 list-detail 规范原文**：

> "On an expanded window, a **visual indicator is essential** to show the relation between the list item and the related details."

**为什么需要你决定**
宽屏下"哪个词对应右边这份详情"需要一眼看出来。规范用的是"essential（必需）"，不是"建议"。

**各选项的代价**
- **甲（保持浅底）**：改动为零。代价是不满足规范措辞，弱视觉下不易辨认。
- **乙（浅底 + 左侧 3px 主色条）**：一眼可辨，改动小。代价是列表行左侧多一条色带，风格上要确认是否与全站一致。

**我的推荐：乙。**

**能否回退**：能。

### 决定 1-6：这一区的 6 项改动是否就是全部范围

**现状与证据**：本轮范围内我列出的是这 6 项：

1. 列表行减少承载信息（决定 1-1），行高随之降到 56 或 72dp（决定 1-4）

**为什么需要你决定**
这是你第 1 点要求的"确认范围"。

**可选项**

- **乙**：在此基础上追加 1-2 与 1-5（列宽与选中指示）——它们同属这一区。
- **丙**：再追加 1-7（见下）。

**我的推荐：乙。** 1-2 和 1-5 都在"额外巩固"以下、都属于对齐与规范一致性，且改动很小。

### 决定 1-7：竖屏的手风琴内嵌详情要不要一并处理

**现状与证据**
竖屏下选中单词时，详情**内嵌展开在列表里**（截图为证：`corruption` 行下方直接接"高频词 / corruption / 音标 / 常用释义 / 真题原句 / 词形变化"）。横屏不是这样。

**各选项的代价**
