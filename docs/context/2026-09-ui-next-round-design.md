## 〇、单位与视口（2026-09-14 实测校正，此前两版都算错了）

设备 HEY2-W09 的实测参数（`adb shell dumpsys window` 的 `overrideConfig`）：

```
densityDpi = 340            devicePixelRatio = 340/160 = 2.125
横屏 overrideConfig: sw753dp w1205dp h721dp  → CSS 视口 1205 × 753
竖屏 overrideConfig: w753dp  h1173dp        → CSS 视口 753 × 1173
物理分辨率 2560×1600（横屏） / 1600×2560（竖屏）
```

换算关系只有这一条（**CSS px 恒等于 dp，这是 Android 的设计前提**）：

```
1 CSS px = 1 dp = 2.125 设备像素
1 设备像素 = 1 / 2.125 = 0.4706 CSS px
```

**我此前犯的两个错**：

1. 先把设备像素当 CSS px 用（第一版）。
2. 又写了一版错误的公式 `CSS = 设备 × (256/densityDpi)`（第二版），得出了 `753 × 471` 这个**方向都反了**的视口。

**正确值**：横屏 CSS 视口 = **1205 × 753**；竖屏 = 753 × 1173。下面凡是涉及数值的结论都按这一条重算。

实测值换算表：

| 量 | 设备像素 | CSS px = dp |
| --- | ---: | ---: |
| 单词列表整列宽 | 794 | **374** |
| 单词详情整列宽 | 1120 | **527** |
| 单词列表行高 | 234 | **110** |
| 列表卡可视高 | 746 | **351** |
| 补缺条高 | 149 | **70** |
| 配置输入框宽 | 924 | **435** |
| 「…」菜单可见部分 | 28 | **13** |

### 视口宽度对"该用几栏"的影响（结论被推翻）

1205 CSS px 宽 **不是** Medium 尺寸类，而是落在更宽的一档：

- Windows 断点：Small ≤640 / Medium 641–1007 / **Large ≥1008** → 1205 属 **Large**。
- Material 3 的栏数推荐：Compact 1 / Medium 1 / **Expanded 2** / Large 2 / XL 2–3。

→ 我此前写"753 属 Medium、双栏是需要说明的取舍"**是错的**。**1205 宽用双栏是有规范支持的正常选择**，不需要特别论证。
→ 同时，"详情栏 632 CSS px 正好等于 WCAG 的中文 40 字上限"这条也随之作废：详情栏实际宽 **527 CSS px**，比上限窄，**这才是可讨论的**。

### 横屏实际可用空间（按正确视口重算）

- 可用宽 = 1205 − 左侧导航栏 76 − 页面左右内边距 `clamp(14px,3vw,34px)`（3vw = 36.15，故取 **34**）× 2 → **≈ 1061 CSS px**。
- 列表双栏实测 374 + 527 = 901，中间还有约 15 的列间距，与 1061 减去列表卡内边距后的量级一致。
- 列表卡可视高实测 **351 CSS px**。

### 列表可见行数（按正确单位重算）

列表卡可视高 351 CSS px ÷ 行高 110 CSS px = **3.2 行** —— 与截图里"看到 3 行 + 第 4 行被裁"完全一致，验证了这套单位是对的。

| 行高 | 可见行数 |
| ---: | ---: |
| 110（现状） | 3.2 |
| 72 | **4.9** |
| 56 | **6.3** |

### 行高与 Material 档位的正确比较

**1 CSS px = 1 dp**，所以行高 **110 dp**。Material 列表三档是 56 / 72 / 88 dp：

- 110 dp **高于三行项 88 dp**，而这行只装 `词条 + 释义 + 词性/状态`（约 2 行语义）。
- 也就是说：**它比"两行项 72dp"高 53%，比"三行项 88dp"还高 25%**，属于**内容只有两行却按三行以上留白**。
- → 所以"压缩行高"确实有余地（与最初那版的直觉一致），但**真正的依据是单位换算后的 dp 比较**，不是我中途基于错误公式给出的"已接近规范上限、不该压"的结论。

下文凡出现"约 620/816 设备像素高"之类的旧表述，一律以本节的 CSS px/dp 值为准。

**跨项目一致的三条结论：**

1. **主流做法是"卡片上只留必要信息 + 分组渐进披露"，而不是给用户一长串字段开关。** qwerty-learner 与 TypeWords 干脆不提供字段开关；Anki 提供了但藏在高级入口。
2. **确实需要字段开关时（备忘录）、按"正面/背面"或按"分组"归类，并明确标出哪些是默认显示。** 这正是当前实现缺的：现在 11 项平铺、只有一行"默认显示"贴在"常用释义"后面、还与被贴的标签重叠 3px。
3. **列表密度上，移动端单词本普遍用"高密度行 + 一行一词"，并让右侧对齐元信息**（掌握度、复习次数）。本项目当前每行 **234 设备像素（≈176 CSS px ≈82.8dp）**，横屏只看得见 3 行 —— 已接近 Material「三行项 88dp」，属每行承载信息过多，而非单纯行高偏大（单位更正见 4.7）。

## 二、统一尺寸规范（token 表）

依据：够用就好、**优先采用代码里已经高频出现的值**，把现有 21 种圆角、8 档按钮高度、21 种字号归并成一套。数值为 CSS px。

### 2.1 关键发现：横屏目前没有自己的尺寸体系

代码级审计（`frontend/src/styles.css` 全文媒体块配对统计）确认：

- Android 专属调优规则**约 78%（1061 行）锁在 `@media (orientation: portrait) and (max-width: 840px)` 里**，横屏完全不生效；横屏只有一个约 48 行的「密度补丁」（`styles.css:6405-6632`）。
- 因此横屏拿到的是**桌面基类**：`--radius-*` 用桌面值 10/14/20/28（竖屏才覆盖成 9/12/16/22，见 `styles.css:28-31` vs `:1742-1749`）、`.card` 内边距 22（竖屏才 15）、`.button` 42px（竖屏才 40）、`.option` 48px/16.5px（竖屏才 44px/14px）。
- 这解释了本轮实机看到的两个现象：同一列表行高 121/122/123（其实是同一个 `min-height:56px` 加文本行盒的亚像素差）、以及**横屏复习卡回落到桌面居中样式**。
- 还发现一个**确定缺陷**：`styles.css:315` 的 `.review-card { min-height: 480px }`，而横屏可用高只有 409px；`.review-overlay`（`:314`）用 `place-items:center` 且**横屏没有 `overflow`**（滚动只在竖屏给，`:1558-1565`）→ 卡片数学上必然溢出且无法滚动。

**结论：规范必须同时建立"方向无关"的基础令牌和一套横屏几何令牌，并把竖屏块里的纯几何部分取消方向门控。**

### 4.6 研究结论（平台规范与同类实现，适用全部版本）

三条来自平台规范与同类实现核实的结论，直接改变上一版的推荐依据：

**① 列表行高：现在的 110 px 不是"列表行"，而是超过"三行列表项"**

Material 官方窗口/列表规格（经 SAP 官方镜像核对）：单行 48、带头像 56、两行 72、三行 88；dense 变体 40/48/60/76；触控目标下限 Material 48×48、Apple 44×44（Apple 原文站点未能打开，经 Fluent 2 转载核实）。

在列表区约 402–409 px 高时：110 → **3.7 行**；88 → 4.5 行；**72 → 5.6 行**；48 → 8.4 行。

→ **只改行高就能把可见行数从 3 提到 4–6 行，不必动结构。** 同类实现参考：TypeWords 的虚拟列表 `min-item-size` 为 90px，列表项 = 单词 + 音标 + 发音 + 中文简释（两行）+ 右侧星标/已掌握图标。所以方案 3 的两行式列表是**有现成范本**的，但行高应取 72 而不是 88。

**② 详情栏宽度：527 CSS px 才是实际值；"横向浪费"的说法不成立**

- 我此前按错误视口算出"详情栏 632 CSS px 正好等于 WCAG 中文 40 字上限"，**该推算作废**。实测详情栏内容宽 **527 CSS px**（=1120 设备像素），**低于** WCAG 的 CJK 上限（16px 中文约 40 字 ≈ 640 px）。
- 也就是说：**详情栏不是"太宽浪费"，而是比可读性上限还窄**，长原句会提前换行。真正偏宽的反而是**左列 374 CSS px 里的列表行**（每行只有一个词条 + 一行释义，却占 374 宽）。
- Material 官方对"单个面板显得空"给的方子仍是："加左右留白，或在面板内按内容做双栏"。按上面的数字，**详情栏保持单栏即可**（还没到需要分栏的宽度），把空间还给正文。

**③ 窗口尺寸类：1205 CSS px 宽属 Large，双栏有规范支持（此前判断作废）**

Material 3 的窗口尺寸类栏数推荐：Compact 1 / Medium 1 / Expanded 2 / Large 2 / XL 2–3；Windows 断点为 Small ≤640 / Medium 641–1007 / **Large ≥1008**。

→ 本机横屏 CSS 视口宽 **1205**，属 **Large**，**双栏是规范支持下的正常选择**。我此前写"753 属 Medium、双栏是需要说明的取舍"是基于错误视口，**作废**。

> 另注：`overrideConfig` 里的 `sw753dp` 是**屏幕最短边**（竖屏宽度），不是横屏宽度。横屏宽度在 `w1205dp`。这是我把视口算反的直接原因。

**④ 例句与出处的标注方式（直接影响"真题原句"回退）**

- WHATWG HTML 规范硬性规定：**"Attribution for the quotation, if any, must be placed outside the `<blockquote>` element"**，官方范式是 `figure > blockquote + figcaption`。
- `<cite>` 的官方定义是**作品标题**，不是出处文字；`cite` 属性必须是 URL 且规范明写 "not for readers"。
- → 所以「2016 · 阅读 Text 4」这类字样应放在 `figcaption`，**不要塞进 `<cite>` 或 `cite` 属性**。这与用户要的"小标签 + 引用框"完全兼容：小标签＝区块标题，引用框＝`blockquote`，出处＝`blockquote` **之外**的 `figcaption`。
- 中文市场现成实现：iciba 的「真题例句」用两种粒度（"出自-2016年12月阅读原文" / "2016年12月六级真题（第一套）阅读 Section C"）；墨墨官方文档写"标注真题出现次数，点击可看年份分布图及真题例句，例句标明年份与题型"。可以照这个粒度做。

**⑤ 渐进披露有一个明确的反例，影响"进阶栏目"的位置**

欧路/Pleco 用"同屏顺次 + 可折叠块 + Tab"；而「不背单词」把例句/词根/派生/真题拆到左右上滑手势里，被竞品分析直接批评"学习过程中不能总览单词全部信息，只能单独对例句、词根、派生词等单一信息查询，对单词用法掌握不利"。

→ **宽屏有空间时，建议默认把「释义 + 真题原句」保持同屏可见**，不要把例句设为默认收起。三个方案都应遵守：默认收起只限"模型例句/记忆提示/三种辨析/词形变化"这批补充内容。

**⑥ 未能核实项（如实标注）**

- m3.material.io 与 developer.apple.com 都是 JS 渲染，本次未能打开原文，分别用 SAP 官方镜像与 Fluent 2 转载核实，属二手引用。

#### 另外两条来自本轮研究、会影响决策的事实

**① M3 对 list-detail 的官方行为规则（一手，值得直接采用）**

- 「By default, in the initial state of a list-detail layout, no list item is selected. However, **we recommend selecting the first item in the list and displaying its details**.」→ 当前实现已经有"宽屏兜底选首条"的行为，**符合规范，保持**。
- 「On an expanded window, a **visual indicator is essential** to show the relation between the list item and the related details.」→ **选中行的视觉指示是"必需项"**，当前只有浅底，建议加左侧主色条。
- 「Each list item ... should include **additional meta information, such as dates, categories, or tags**, to allow users to search and sort quickly.」→ **列表行该带元信息**（学习状态就是），所以不建议把行压到只剩单词。
- 「in a list-detail layout, the list should have a **fixed width**, while the detail pane should be **flexible**」→ 当前是 `.85fr : 1.2fr` 两个都弹性，**建议左列改固定宽、右列吃剩余**。
- 「**If only one detail pane is displayed, we recommend adding left and right padding or using a dual-column layout within the pane to prevent the content from stretching.**」→ 面板内双栏是官方认可手段，但要按内容分（不建议把中文释义切两栏，因为 632px 单栏已恰好等于 WCAG 的 CJK 上限）。

**② Anki 的"列表层 ≠ 详情层"官方先例（直接支持减少行内信息）**

Anki 的 **Browser Appearance** 功能原文：允许"define a custom template to be used **only in the browser**"，以便"**include only the important fields** and change the order"。→ 也就是说**"列表行用一套精简字段、详情面板用完整字段"是成熟产品里的标准做法**，不是我们为了让行变矮而做的妥协。这条是本轮第 1 项改动的正式依据。

**③ 需要警惕的两个已知反模式**

- **把例句/搭配/词形/辨析拆进多个手势或 Tab**：「不背单词」这么做，被产品分析直接批评"学习过程中不能总览单词全部信息，只能单独对例句、词根、派生词等单一信息查询，对单词用法掌握不利"。→ 我们保留"详情栏同屏顺次 + 可折叠块"是对的，**不要把进阶栏目改成 Tab 或手势**。
- **把"紧凑视图"设为默认**：M2 原文"48 x 48 dp minimum touch targets **should be the default experience** … Users **must opt in** to high density component experiences because higher density components **do not meet accessibility requirements**"，MDC 更直接"Touch targets are automatically disabled when density mixins are applied"。
  → 本轮我们做的是**把每行信息量降到规范档位**（从三行语义降到一至两行），**不是启用高密度模式**，所以不存在这条无障碍问题。但如果以后要做"紧凑/宽松"两档，**默认必须是宽松档 + 用户主动开启**。这一点我会写进实现说明。

**④ 关于搜索框与详情栏宽度的补充依据**

- 搜索框：Material 把这类单一动作输入框叫 **solo field**，原文"An input line is not required" —— 所以 639px 的问题是"**空**"不是"**长**"。本轮不动它（在"额外巩固"以上，属保持区），但记录下来。
- 行长：WCAG 2.2 SC 1.4.8 原文"Width is **no more than 80 characters or glyphs (40 if CJK)**"。632px 对 16px 中文 ≈ 40 字/行，**正好在上限**，所以**单栏是正确选择**。另 GitLab 的实测结论是最佳文本宽度 ≈ 580–720px（16px 字号），632 也在区间内。

**⑤ 仍未核实**

- Apple HIG 不发布列表行高（已确认）；M3 没有列表 density 刻度（已确认）；NN/g 与 Fluent 都没有行高数值（已确认）。
- 设备端 `devicePixelRatio` 本轮**已由实测尺寸反推为 2.125**（见上文），但未在设备上直接读取 `window.devicePixelRatio`，实现前建议顺手确认一次。
